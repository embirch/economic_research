# Clio: A system for privacy-preserving insights into real-world AI use

*The methods substrate of the Economic Index. Every Index release runs on this system. This entry is written for one purpose: to record, from the primary sources, **what the classifier and the privacy pipeline can and cannot see** — because every number in every Index report is an output of the machinery described here.*

## Claims

Numbered claims with page or figure reference, the number as published, and the comparison each rests on. Paper page numbers are PDF pages (printed and physical pagination coincide). Web claims are tagged **[web]** and carry their section.

**The system's headline validation claims**

1. **94% reconstruction accuracy on synthetic data.** "Clio reconstructed the ground-truth distribution of topics in a synthetic dataset with 94% accuracy" (§1, p.2). Restated §2.2 (p.5): "Clio is able to accurately reconstruct these categories with 94% accuracy, giving us confidence in its results." Figure 4 caption (p.6): "Clio reconstructs ground-truth categories on an evaluation dataset of 19,476 synthetic chat transcripts with 94% accuracy, compared to 5% for random guessing." *Comparison: Clio's reconstructed topic distribution against a known ground-truth distribution, on **synthetic** data, with **random guessing at 5%** as the floor. 5% = 1/20, the reciprocal of the 20 top-level categories (checked by the wiki author). The comparison is the finding: 94 against 5, not 94 against any competing method.*
2. **84% on concerning synthetic data — a 10-point drop.** "We find that Clio achieves 94% accuracy across 20 high-level clusters on regular synthetic data and 84% accuracy across 18 high-level clusters on concerning synthetic data" (C.2.2, p.28). *Comparison: regular against concerning synthetic data, same pipeline. The paper attributes the drop partly to the subject and partly to the instrument: "While Claude's evasiveness likely explains some of the performance decrease on concerning data, we believe that some of the performance decrease is also a result of the synthetic data itself being lower quality, also due to model evasiveness." The 84% is the only headline accuracy figure that never appears in the abstract, §1, §2.2 or the web post.*
3. **Reconstruction accuracy above 92% in every one of 15 languages.** "Clio's performance is consistent across languages. We find that Clio maintains overall accuracy above 92% across all languages we tested" (C.2.2, p.28). Table 5 (p.29), accuracy / macro-avg F1 / weighted-avg F1 / samples, as published: English 0.954 / 0.954 / 0.955 / 1,354; Ukrainian 0.952 / 0.956 / 0.952 / 1,243; Spanish 0.950 / 0.952 / 0.950 / 1,283; Japanese 0.944 / 0.943 / 0.945 / 1,297; Mandarin Chinese 0.942 / 0.942 / 0.943 / 1,296; French 0.942 / 0.946 / 0.942 / 1,260; Russian 0.941 / 0.938 / 0.941 / 1,261; Hindi 0.941 / 0.937 / 0.941 / 1,330; Portuguese 0.941 / 0.947 / 0.942 / 1,343; Catalan 0.941 / 0.946 / 0.942 / 1,299; Armenian 0.939 / 0.934 / 0.939 / 1,302; Arabic 0.939 / 0.940 / 0.939 / 1,294; Afrikaans 0.937 / 0.936 / 0.938 / 1,295; Turkish 0.935 / 0.940 / 0.935 / 1,357; Georgian 0.927 / 0.933 / 0.927 / 1,262. Table 5 caption: "Clio has strong multilingual performance, with reconstruction accuracy above 92% on all tested languages." *Comparison: fifteen languages against each other and against the 92% floor. **The spread is 2.7 points, English to Georgian (0.954 − 0.927), and English is top.** No interval is given on any cell; on ~1,300 samples a 95% binomial interval around 0.94 is roughly ±1.3 points, so most of the language ranking is not separable — the wiki author's calculation, offered only to show that the ranking is not a finding. The sample column sums to exactly 19,476, matching the synthetic dataset size (checked).*
4. **Every pipeline stage validated by manual review at 96–97%.** Table 4 (p.26), "Accuracy or correlation of different stages of Clio's pipeline with the ground truth (manual review)", columns Combined Accuracy / Random Data / Concerning Data: **Extractor (Summaries)** 96% / 93% / 98%; **Extractor (Concerning Content ID)** — / 0.84\* (\*Spearman's Rank Correlation); **Base-level Clusterer** 97% / 99% / 96%; **Hierarchical Clusterer** 97% / 95% / 99%. *Comparison: model output against human raters, split by whether the input was randomly sampled or Trust-and-Safety-flagged. Note the **direction reverses across stages**: summarisation and hierarchical clustering are **better** on concerning data, base-level clustering **worse**. The paper does not remark on this.*
5. **Summary accuracy: 96% of 200 conversations.** "we manually reviewed 200 conversations without associated metadata and each conversation's Claude-written summary… we asked raters to assess 'whether the summary accurately reflects the exchange.' Of the 200 conversations we reviewed, half were randomly sampled from Claude.ai Free and Pro, and half were random conversations whose last turn were flagged by Anthropic's automated Trust and Safety tooling for being potentially harmful… We found that 96% of the conversations were summarized accurately, including 93% of the random conversations and 98% of the concerning conversations" (C.1.1, p.26). *Comparison: random against flagged, n = 100 each. **On 100 observations, 93% carries a 95% interval of roughly ±5 points** (wiki author's calculation), so 93 against 98 is not a separable difference. The named failure mode is the one that matters most downstream: "long, multi-topic conversations where the summary sometimes omitted a subset of the requests from the user in the conversation (in these instances, the model would typically focus on the more harmful requests, if any existed)."*
6. **Concern-score agreement: Spearman ρ = 0.84.** "We found that Claude's assessment and our manual assessment had a Spearman's correlation coefficient of 0.84, indicating strong directional agreement" (C.1.2, p.26), on "the same set of 200 conversations as above", ranking harmfulness 1–5. *Comparison: model scores against human scores, rank-order only. The paper states why: "We evaluate the correlation rather than other measures of inter-annotator agreement because the downstream use of these scores is as a comparative indicator." **No exact-agreement rate, no weighted kappa, no confusion matrix is published for the 1–5 scale.***
7. **Base-level cluster titles accurate for 99% (random) and 96% (flagged) of clusters.** "We manually reviewed 5,904 cluster assignments across 183 distinct clusters. Of those 183 clusters, 100 were generated from random Claude.ai conversations, and were 83 generated from content flagged by Trust and Safety… Overall, we found that 99% of clusters on random Claude.ai conversations had accurate titles, and 96% of the clusters on conversations flagged by Trust and Safety had accurate titles" (C.1.3, p.26). Named failure mode: "The most common reason Trust and Safety-flagged conversations were rated inaccurate is that the cluster title was overly generic in referring to the type of harm." *100 + 83 = 183 ✓ (checked). The grammar "and were 83 generated" is the source's.*
8. **3% of conversations in the average cluster do not belong there.** "We found that an average of 3% of the conversations in each cluster did not clearly belong to that cluster. Often these incorrect assignments were subtle and not obviously wrong: For example, the cluster 'analyze business case studies' might incorrectly include a conversation where the user asks Claude to analyze a stock, but not as part of a business case study" (C.1.3, p.27). *Comparison: none — a single misassignment rate. **This is the most consequential number in the paper for downstream economic measurement and the one the Index reports never quote:** every task-share, occupation-share and collaboration-share the Index publishes is a count over cluster memberships whose measured contamination is ~3% on average, with no dispersion published across clusters and no statement of whether contamination is random or systematic across cluster sizes.*
9. **Hierarchical cluster titles accurate for 97%.** "We manually reviewed 1,094 hierarchical cluster assignments across 183 distinct higher-level clusters. Of those 183 clusters, 100 were generated from random Claude.ai conversations, and were 84 generated from content flagged by Trust and Safety. We found that 97% of the hierarchical clusters' titles accurately reflected their contents. 95% of hierarchical clusters on random Claude.ai conversations were accurate, and 99% of hierarchical clusters on conversations flagged by Trust and Safety were accurate" (C.1.4, p.27). ***Arithmetic error in the source: 100 + 84 = 184, not the stated 183** (checked by the wiki author; C.1.3's parallel sentence gives 83 and sums correctly). Off by one; recorded, not corrected.*
10. **Auditor accuracy: 98% on a curated hard test set.** "we created a test set of 1,237 examples (630 not privacy preserving, 607 privacy preserving)… Results from these validation efforts showed that the auditor achieved a 98% accuracy rate on our hand-designed test set" (D.1, p.32), where the task is "measured as a binary classification task of whether the example was rated 3 or above on the privacy scale in Table 6". Restated §D (p.31): "showing that it achieves 98% accuracy on a hard test set of examples we curated." *630 + 607 = 1,237 ✓ (checked); the set is near-balanced (50.9% / 49.1%), so 98% is well above a majority-class baseline. **But the negatives are synthetic:** "the non-privacy preserving clusters were created by taking privacy-preserving clusters and subtly editing them to introduce fictional private information inserted into them using a combination of models and manual annotation" (D.1, p.32). The comparison is therefore auditor against an adversarial set the authors built, not against naturally occurring privacy failures.*

**The privacy audit results**

11. **~10% of raw conversations contain private information.** "Baseline: We established a baseline rate by measuring the rate of private information in raw user conversations. We observed that approximately 10% of raw data contained private information (rated as 1 or 2 out of 5 on our privacy scale)" (§D, p.31). *Comparison: this is the denominator the other two stages are measured against.*
12. **Summarisation cuts it to ~1.5%.** "Post-summary: After applying summarization, the rate of private information dropped to about 1.5%" (§D, p.32). *Comparison: post-summary against the ~10% baseline — a factor of roughly 6.7 (wiki author's arithmetic).*
13. **After cluster summarisation, nothing is rated 3 or below.** "Post-cluster summary Following the cluster summary step, almost all clusters were rated 5, with a few instances rated 4, and none rated 3 or below. This is the final and most important step, as these cluster summaries are visible to analysts who use Clio" (§D, p.32). Stated in §1 (p.2) as: "produced no clusters with private data in an audit of 5,000 conversations". Figure 5 caption (p.7): "Progression of privacy scores (see Table 6) across different layers in Clio for an analysis of 5,000 Claude.ai conversations. At the point where Clio's outputs are visible to analysts (Cluster Summaries) the amount of private information (1s and 2s, shaded region) reaches very low levels." *Comparison: the three pipeline stages against each other. **Two things to hold onto.** First, the §1 and caption framings differ in strength: §1 says "no clusters with private data"; the caption says "very low levels"; §D says "none rated 3 or below". Second, **the audit's own thresholding means the claim is about a rubric, not about re-identification**: "3" is defined as "Contains specifics that narrow identification to several thousand people" and counts as acceptable (Table 6, p.32; §D, p.31).*
14. **The audit sample size is stated two different ways.** §D (p.31): "We ran the automated privacy auditor at three different stages of our pipeline, across a sample of **5,000** conversations". Figure 5 caption (p.7): "an analysis of **5,000** Claude.ai conversations". §1 (p.2): "an audit of **5,000** conversations". Table 7 (p.37): "Privacy Benchmarking — **25,000** — Strategy 1 — Nov 8–Nov 14, 2024 — §D, Fig. 5". *Divergence recorded, neither version treated as governing, per `room/director-2026-09-16-pdf-web-ruling.md`. **No post that cites the privacy audit should give its sample size without saying that the paper states it twice as 5,000 and once, in the run table that is supposed to be authoritative for it, as 25,000.** The most natural reconciliation — 25,000 sampled, 5,000 audited — is nowhere stated in the paper and is the wiki author's conjecture, not a finding.*

**Cluster counts and the cost of a run**

15. **Thousands of clusters, presented at three levels.** "Clio can identify thousands of different clusters in a dataset" (§2.2, p.5); "Using the Clio facet 'What task is the model being asked to perform in this conversation?'… Clio surfaced thousands of clusters corresponding to the different tasks represented in user's conversations with Claude.ai" (§3.1, p.7); "In addition to the high-level clusters we identified in Claude.ai, Clio also identified thousands of more granular usage clusters" (§3.2, p.8); "In practice, k can be quite large, including many thousands of clusters" (B.2, p.23). Hierarchy depth for the worked example: "These clusters are recursively assigned to higher-level clusters twice, to create a bottom-up hierarchy of clusters with three levels" (Table 1 caption, p.24). *Comparison: none. **No exact cluster count is published for any run in this paper**, and the number of clusters k is deliberately withheld (see Claim 21). For contrast, the second Index release publishes an exact count — "630 granular clusters… organized into three levels of hierarchy" (`wiki/reports/economic-index-2025-03-report.md` Claim 13).*
16. **A 100,000-conversation run costs $48.81.** "In Table 3 we provide an estimated breakdown of the cost of a Clio run. For our example run of 100,000 conversations, the cost of such a run is $48.81, demonstrating the relative affordability of this method for scaling to large datasets" (§2.2, p.6). Table on p.25, as published — step / model / input tokens / output tokens / input cost / output cost / total: **Facet Extraction** / 3 Haiku / 130.0M / 10.0M / $32.50 / $12.50 / **$45.00**; **Cluster Labeling** / 3.5 Sonnet / 1.0M / 50.0K / $3.00 / $0.75 / **$3.75**; **Hierarchy Generation** / 3.5 Sonnet / 18.0K / 600.0 / $0.05 / $0.01 / **$0.06**; **Estimated Total $48.81**. Notes to the table: "Costs calculated using Claude 3 Haiku ($0.25/MTok input, $1.25/MTok output) and Claude 3.5 Sonnet ($3/MTok input, $15/MTok output) pricing. Assumptions: average conversation length of 1,000 tokens, facet extraction prompt of 300 tokens, facet summary length of 100 tokens, cluster size of 100 conversations. Hierarchy organized into three levels (10 top-level categories → 100 mid-level → 1000 leaf clusters). Cost per conversation: $0.0005." *Comparison: implicitly against human review, which is never costed. **Arithmetic checks by the wiki author:** 45.00 + 3.75 + 0.06 = 48.81 ✓; 48.81 / 100,000 = $0.000488, consistent with the stated $0.0005 ✓; facet-extraction input 100,000 × (1,000 + 300) = 130.0M ✓; output 100,000 × 100 = 10.0M ✓; 130 × $0.25 = $32.50 ✓ and 10 × $1.25 = $12.50 ✓. **Two internal inconsistencies, also the wiki author's arithmetic and not the paper's:** at a cluster size of 100 conversations, 100,000 conversations give 1,000 base clusters, and Appendix G.5 (p.39) states that each labelling call is given "a random sample of 50 summaries from records within the cluster, as well as 50 summaries of records that are closest to the centroid of the cluster but not assigned to the cluster" — 100 summaries × 100 tokens ≈ 10,000 input tokens per cluster, i.e. ~10M for 1,000 clusters, about **ten times** the table's 1.0M. Likewise 18.0K input tokens for hierarchising 1,000 leaf clusters is below the token cost of merely listing 1,000 cluster names and descriptions. The $48.81 should therefore be read as a lower bound on the marginal inference cost of the pipeline as the paper itself specifies it, and it excludes embedding, clustering, UMAP, engineering, storage and the secure-environment infrastructure entirely.*

**What the 1M-conversation Claude.ai run found**

17. **"Web and mobile application development" is over 10% of all conversations.** "As shown in Figure 6, which displays the top ten of these top-level categories, we see a particular emphasis on coding-related tasks, with the 'Web and mobile application development' category representing over 10% of all conversations" (§3.1, p.7). **[web]** §Top use cases on Claude.ai: "This revealed a particular emphasis on coding-related tasks: the 'Web and mobile application development' category represented over 10% of all conversations." *Comparison: one top-level category against the other nine. Figure 6 caption (p.8): "Top 10 high-level task categories in a random sample of 1M Claude.ai conversations." Base: 1,000,000 conversations, Claude.ai Free and Pro, **Oct 17–Oct 24, 2024** (Table 7, p.37). **This is the direct ancestor of the Index's coding finding** — cf. `wiki/reports/economic-index-2025-02-report.md`, where the same emphasis is expressed through the O\*NET taxonomy. Note the construct is a **Clio-generated bottom-up category**, not an O\*NET task group: the two are not the same measure and are not comparable without a mapping.*
18. **Writing, research and education each 6–10%.** "We also noticed a high percentage of writing, research, and educational usage, each comprising 6-10% of usage" (§3.1, p.7). *Comparison: three categories given one shared band, so no ordering among them is published.*
19. **[web] The same finding, with two point figures the paper does not give.** "Educational uses formed another significant category, with more than **7%** of conversations focusing on teaching and learning. A substantial percentage of conversations (nearly **6%**) concerned business strategy and operations (including tasks like drafting professional communications and analyzing business data)." (§Top use cases on Claude.ai.) *Divergence recorded: the paper publishes a 6–10% band for writing/research/education and no business-strategy figure; the post publishes ">7%" for education and "nearly 6%" for business strategy. **Neither is governing** (`room/director-2026-09-16-pdf-web-ruling.md`). Note also that "business strategy and operations" is not among the three categories the paper bands at 6–10%, so the post reports a fourth category the paper's prose omits.*
20. **Coding is 15–25% across the two public comparison datasets.** "We also analyzed the distribution of tasks in popular public datasets LMSYS-1M-Chat [Zheng et al., 2023] and WildChat [Zhao et al., 2024]–which are included in Appendix E. While coding remains a consistently popular use-case across all datasets (representing 15-25% of conversations), the datasets show marked differences in their other dominant use cases, with WildChat containing a large number of requests to produce image-generation prompts and LMSYS containing more conversations that explicitly test model capabilities and boundaries" (§3.1, pp.7–8). Restated in Appendix E (p.33): "We found the distribution of Claude.ai usage to significantly differ from that of WildChat and LMSys as seen in Figure 15… More similar to Claude.ai usage, coding use cases were common across both datasets—totaling 15-25% of conversations." *Comparison: Claude.ai against WildChat against LMSYS-Chat-1M, on the same Clio pipeline. **This is the paper's only external-validity comparison and the only place any Anthropic publication benchmarks Claude.ai usage composition against a non-Anthropic corpus.** The word "significantly" is used without a test. The 15–25% band covers both public datasets and is not reported separately for either, and no equivalent band is given for Claude.ai, so the comparison cannot be made numerically from the prose.*
21. **The number of clusters k is deliberately withheld.** "We vary k based on the number of conversations in the input dataset; we unfortunately cannot provide our precise values for k (as this information could be used to determine the volume at which coordinated behavior would likely not be caught by Clio as a distinct cluster)" (G.5, p.39). *Not a finding but a published non-disclosure, and the single largest barrier to external replication of any Clio-derived number. It also means the granularity of every published Index cluster count is unreproducible in principle.*
22. **Claude usage differs by language, expressed as a ratio to a base rate.** "Our analysis revealed that certain topics were significantly more prevalent in non-English conversations compared to English ones. These included discussions of economic issues (e.g., *Explain and analyze economic theories and their real-world applications*), social issues (e.g., *Research and develop solutions for aging populations and elderly care*), ure (e.g., *Create and analyze anime and manga content and related projects*)" (§3.3, p.8; the truncated word "ure" — presumably "culture" — is the source's). Figure 7 caption (p.9): "Common clusters across languages. This figure highlights clusters with disproportionately high prevalence of Spanish, Chinese, and Japanese. **Ratios represent the prevalence of the language within the cluster compared to the base rate of the language in the overall sample.** These results are based on a sample of Claude.ai consumer conversations." **[web]** §Claude usage varies by language: "We calculated a base rate of how often each language appeared in conversations overall, and from there we could identify topics where a given language appeared much more frequently than usual." Caption: "Conversation topics that appeared more frequently in three selected languages (compared to the base rate of that language), as revealed by Clio." *Comparison: within-cluster language share against that language's overall share — **a ratio-to-base-rate construct that is the direct methodological ancestor of the Index's AI Usage Index** (AUI = a geography's share of Claude usage ÷ its share of working-age population; `/mnt/memory/standards/terminology.md`). The same normalisation logic, one construct earlier. Base: 2,281,911 conversations, Strategy 1, **Oct 24–Nov 13, 2024** (Table 7, p.37). **No ratio value is recorded here**: every number in Figure 7 exists only inside a raster image, and "significantly" is again used without a test.*
23. **The abstract, §1 and §8 each name a different lead multilingual example, and one of them appears nowhere in §3.3.** Abstract (p.1): "conversations in Japanese discuss elder care and aging populations at higher-than-typical rates". §1 (p.3): "Japanese and Chinese conversations are more likely to discuss elder care." §8 (p.16): "significant variations in cross-language usage (e.g., **higher use of language learning in non-English languages**)". *Internal inconsistency recorded: **"language learning" is not among the three topic families §3.3 reports** (economic issues, social issues, culture), and no language-learning cluster is named anywhere in the paper's text. Anyone citing the paper's multilingual finding should cite §3.3 or Figure 7, not §8.*
24. **Clio clusters are not guaranteed to be unique.** "Clio clusters are not guaranteed to be unique. Because multiple Clio clusters may describe the same behavior, it is possible that there are other clusters similar to the ones presented in Figure 7 with different language distributions" (footnote 4, p.9). *Not a result but a bound on every result: **a cluster's share is not the share of the behaviour it describes**, because the same behaviour may be split across clusters. **Cluster**

- "**Semantic clustering**: Clio then groups similar conversations by creating embeddings [Reimers and Gurevych, 2019, 2022] of one of the natural language facets (e.g., conversation topic) and using k-means clustering [Lloyd, 1982]." (§2.2, p.4.)
- "**Describe clusters**: Each cluster is given a descriptive title and summary using a model, which examines sample conversations from the cluster to identify common themes while excluding any private information." (§2.2, p.5.)
- "To identify meaningful patterns in Claude usage, Clio employs semantic clustering on summary facets. This approach allows us to group similar conversations based on their high-level content and intent, rather than specific details that might compromise privacy. The process involves two main steps: embedding and clustering. First, we create embeddings from the summary facets, such as user intent or conversation topic. These embeddings are dense vector representations that capture semantic meaning; conversations will have similar embeddings depending on their summary. **The choice of summarization prompt (e.g., *What is the overall topic of the conversation?* or *What is the user's prompting style?*) controls the information extracted in the summaries, and thus influences which conversations get placed close together in the embedding space.**" (B.2, p.22.)
- "For clustering, we primarily use the k-means algorithm due to its efficiency and effectiveness for our use case. While we experimented with other clustering methods, we found that k-means works surprisingly well for identifying neighborhoods in **what is fundamentally a continuous manifold of conversation types, rather than discrete, well-separated clusters**." (B.2, pp.22–23.) *The last clause is the paper's own statement that its clusters are cuts through a continuum, not natural kinds — and therefore that any cluster boundary, and any share computed over it, is a choice of k.*
- "The number of clusters k is a key parameter that we adjust based on the size of the dataset. In practice, k can be quite large, including many thousands of clusters. To ensure privacy, we aggregate data not only by semantic similarity but also by enforcing a minimum number of unique users per cluster. This dual approach to aggregation helps prevent the identification of individuals or small groups within the data." (B.2, p.23.)
- **Embedding and clustering, at parameter level** — "For non-categorical or numeric facets (e.g., our request facet), we first embed each extracted summary using **all-mpnet-base-v2** [Reimers and Gurevych, 2022], a sentence transformer model that provides **768-dimensional** embeddings. We then generate base-level clusters by running k-means in embedding space. We vary k based on the number of conversations in the input dataset; we unfortunately cannot provide our precise values for k…" (G.5, p.39.)
- **Cluster naming, at parameter level** — "We then use Claude to generate a name and description for each cluster. We use **Claude 3.5 Sonnet (June 2024; claude-3-5-sonnet-20240620) with a temperature of 1** and provide a random sample of **50 summaries from records within the cluster, as well as 50 summaries of records that are closest to the centroid of the cluster but not assigned to the cluster**. We then ask Claude to generate a name and description for the cluster that identifies the records within the cluster and differentiates them from the summaries outside of the cluster" (G.5, p.39). The naming instruction, verbatim in part: "Summarize all the statements into a clear, precise, **two-sentence description in the past tense**. Your summary should be specific to this group and distinguish it from the contrastive answers of the other groups. After creating the summary, generate a short name for the group of statements. **This name should be at most ten words long** (perhaps less) and be specific but also reflective of most of the statements (rather than reflecting only one or two)… Be as descriptive as possible and assume neither good nor bad faith. Do not hesitate to identify and describe socially harmful or sensitive topics specifically; specificity is necessary for monitoring." And the per-facet naming criterion, quoted in full: "Criteria refers to natural-language requirements for the names and descriptions of each cluster. For our Request facet, for example, we require that "The cluster name should be a sentence in the imperative that captures the user's request. For example, 'Brainstorm ideas for a birthday party' or 'Help me find a new job.'"" (G.5, p.39.)
- **Cluster non-uniqueness** — "Clio clusters are not guaranteed to be unique. Because multiple Clio clusters may describe the same behavior, it is possible that there are other clusters similar to the ones presented in Figure 7 with different language distributions." (Footnote 4, p.9.)

**Hierarchy**

- "**Building hierarchies**: Clio can identify thousands of different clusters in a dataset. To make it manageable to explore this many clusters, Clio organizes these clusters into a multi-level hierarchy using a method that combines k-means clustering and prompting (see Appendix G.7). This hierarchy allows users to start with broad categories (e.g., *Writing assistance*) and progressively drill down into more specific insights (e.g., *Assistance writing a dark comedy.*)" (§2.2, p.5.)
- "**Hierarchical organization of patterns** Clio is designed to be scalable to many millions of conversations. To enable users to navigate large numbers of patterns discovered in a vast dataset, Clio recursively organizes base-level clusters into a multi-level hierarchy that lets users start from a set of a few dozen high level patterns (e.g., *Explain scientific concepts and conduct academic research*) to thousands of lower-level categories (e.g., *Explain and analyze cancer immunology research and treatments*)." (§2.1, pp.3–4.)
- **[web]** "**Building hierarchies**: Clusters are organized into a multi-level hierarchy for easier exploration. They can then be presented in an interactive interface that analysts at Anthropic can use to explore patterns across different dimensions (topic, language, etc.)." (§How Clio works.)
- **The hierarchiser algorithm, in full** (G.7, p.40) — "Clio's hierarchizer transforms base clusters (described in Appendix G.5) into a hierarchy. The hierarchizer iteratively creates new levels clusters (which contain the previous level of clusters as children) until the number of top-level clusters is within the desired range. We also explored other hierarchical clustering algorithms (such as HDBSCAN [McInnes et al., 2017] and agglomerative clustering methods) but found the results inferior to the Claude-based approach." Then, at each level *l*:
  - "**Embed clusters.** Embed each cluster's name and description using the all-mpnet-base-v2 [Reimers and Gurevych, 2022] sentence transformer to obtain 768-dimensional vector representations of each cluster."
  - "**Generate neighborhoods.** Group these embeddings into k neighborhoods using k-means clustering, where **k is chosen so that the average number of clusters per neighborhood is 40**. We group clusters into neighborhoods because the names and descriptions for all base clusters may not fit within Claude's context window."
  - "**Propose new clusters for each neighborhood.** For each neighborhood, use Claude to propose candidate higher-level cluster descriptions by examining both the clusters within the neighborhood and the nearest m clusters outside it. Including the nearest clusters beyond the neighborhood ensures that clusters (or groups of clusters) on the boundary between neighborhoods are neither overcounted nor undercounted. We require the final number of clusters at the level l to be n*l* ± 1.5n*l*, where n*l* is chosen such that the ratio between successive levels follows n*l*/n*l−1* = (n*top*/n*base*)^(1/(L−1)) for L total levels." *(Transcription note: the subscripts are rendered inline here; the formula and the "± 1.5n*l*" tolerance are as printed, and the tolerance as printed admits a negative lower bound, which is presumably a typesetting slip for a multiplicative band.)*
  - "**Deduplicate across neighborhoods.** Deduplicate and refine the proposed clusters across all neighborhoods using Claude to ensure distinctiveness while maintaining coverage of the underlying data distribution."
  - "**Assign to new best fit higher-level cluster.** Assign each lower-level cluster to its most appropriate parent cluster using Claude. We randomly shuffle the order of the higher-level clusters when sampling from Claude to avoid biasing assignments based on the order of the list."
  - "**Rename higher level clusters.** Once all clusters at level l have been assigned to a higher-level cluster, we regenerate a new name and description for the parent cluster based on the lower-level clusters that were assigned to it. This renaming step ensures that cluster names continue to accurately reflect their contents."
  - "This process continues until reaching the desired number of top-level clusters k*top*. The resulting hierarchy enables exploration at multiple levels of granularity while preserving semantic relationships between clusters."
- **The forced-assignment rule** — from the assignment prompt (G.7.1, pp.43–44): "**You MUST assign the specific cluster to the best higher-level cluster, even if multiple higher-level clusters could be considered.**" *There is no "other", no "none of the above" and no multi-parent option: every lower-level cluster gets exactly one parent. Any "unclassified" residual in a downstream Index table therefore comes from a different stage, not from hierarchisation.*
- **Hierarchiser parameters** — "Our hierarchizer used Claude 3.5 Sonnet (June 2024; claude-3-5-sonnet-20240620) with a temperature of 1.0." (G.7.1, p.41.)
- **Worked example of the three levels** (Table 1, p.24, one row quoted in full): "CONVERSATION: "Human: how can solve gpu consume when use trainer.train for finetuning llm" / SUMMARY: The user's overall request for the assistant is to provide code or guidance on how to reduce GPU consumption when fine-tuning a large language model. / CLUSTERING: Base: *Provide technical guidance on large language model development and implementation* — Intermediate: *Implement and explain machine learning algorithms and models* — Top: *Explain concepts and solve problems across diverse fields*". Table 1 caption: "We provide example conversations from WildChat and the pipeline to assign them to clusters. Clio extracts summaries of individual conversations, which it groups into clusters (as described in Appendix B) These clusters are recursively assigned to higher-level clusters twice, to create a bottom-up hierarchy of clusters with three levels." (The missing full stop after "Appendix B)" is the source's.) *Note in this example that a coding conversation's **top-level** label is "Explain concepts and solve problems across diverse fields" — the same top-level cluster to which the table assigns a philosophy conversation. The hierarchy's top level is not a taxonomy of subject matter.*

**Privacy: the thresholds, the aggregation rules and the auditor**

- **The privacy objective and the definition of private information** — "Perhaps the most critical design objective for Clio is privacy. Clio's design promotes user privacy by generating high-level insights that do not contain or reveal any private user information. **We define private information broadly to be any information that could identify not just individual people but also small numbers of individuals or specific organizations (e.g. a small 100-person village or a small 15-person business; see Table 6 for details).**" (§2.3, p.6.)
- **Why no formal guarantee** — "Because Clio produces rich textual descriptions, it is difficult to apply formal guarantees such as differential privacy [Dwork et al., 2006] and k-anonymity [Sweeney, 2002]. Thus, we take a **statistical and empirically validated approach to privacy**, designing a set of privacy layers to preserve and enhance privacy at all levels of the system. While no single layer can perfectly guarantee user privacy, together they serve as defense in depth, collectively driving the error rate of the system to undetectable levels on our internal privacy evaluations (described in Appendix D)." (§2.3, p.6.)
- **The four privacy layers, in full** (§2.3, p.7):
  1. "**Conversation summary step**: The model is prompted to answer the requested summarization question (e.g., what is the topic of the conversation?) while omitting any private information."
  2. "**Cluster aggregation thresholds**: Clusters are only retained if they exceed minimum size requirements for both unique accounts and conversations. In other words, clusters that are composed of only a single or small number of accounts will be discarded."
  3. "**Cluster summary step**: When generating cluster summaries, the model is again instructed not to include private information."
  4. "**Cluster auditing**: A model reads cluster summaries and removes all clusters with any private information."
  - Followed by: "These measures work in concert to create multiple layers of privacy protection throughout the Clio pipeline. As Figure 5 shows, together these results enable driving down the amount of private information exposed in Clio to undetectable levels."

## Data and methods

The wiki author's words, with references to the two documents.

- **What kind of study this is.** A systems paper with a validation suite and two demonstration applications. No hypothesis, no pre-registration, no identification strategy, no statistical inference of any kind: the paper reports accuracies, two correlations and descriptive shares, and nothing else. There is no standard error, confidence interval, significance test or power calculation anywhere in 46 pages. The word "significantly" appears twice as a description of a difference (§3.3, p.8; Appendix E, p.33) and both times without a test.
- **Pipeline, in the order the paper gives it** (§2.2, pp.4–5; Appendix B, pp.22–23; Appendix G, pp.36–46):
  1. **Input and sampling.** Random sample of Claude.ai Free and Pro conversations, Teams/Enterprise/API and Zero Retention accounts excluded. Two strategies (Claim 36); optional screener stage narrowing the sample by a Claude yes/no question (G.3).
  2. **Preprocessing.** Transcript standardised into XML; function calls, system prompts, multimodal content and metadata given unspecified "special handling" (G.2).
  3. **Facet extraction.** One or more facets per conversation. Model-extracted facets go through the extractor prompt, which forbids PII and proper nouns, forces English output, and caps the answer at two sentences. Computed facets (turn count) bypass the model. Four facets used in this paper: Request, Language, Task, Concerning.
  4. **Embedding.** `all-mpnet-base-v2`, 768 dimensions, applied to the *summary*, never to the conversation.
  5. **Base-level clustering.** k-means over embeddings; k withheld.
  6. **Cluster naming and description.** Claude 3.5 Sonnet (June 2024), temperature 1, shown 50 in-cluster and 50 nearest-outside summaries, asked for a ≤10-word imperative name and a two-sentence past-tense description that distinguishes the cluster from its neighbours.
  7. **Aggregation thresholds.** Clusters below minimum unique accounts *and* conversations discarded. Values withheld.
  8. **Hierarchisation.** Iterative embed → k-means neighbourhoods of ~40 → Claude proposes parents → Claude deduplicates → Claude force-assigns each child to exactly one parent (shuffled order) → Claude renames parents. Claude 3.5 Sonnet (June 2024), temperature 1.0.
  9. **Privacy auditing.** Claude 3.5 Sonnet (June 2024), temperature 0.05, scores each cluster name+description 1–5; clusters below 3 removed.
  10. **Projection and interface.** UMAP (n_neighbors 15, min_dist 0, cosine) to 2D; map view, tree view, faceted/temporal breakdowns, facet overlays; "traces" drill-down for non-sensitive data or authorised staff only. The projector "does not affect any results in this paper" (G.6, p.40).
- **Models used, exhaustively, as named in the paper.** Facet extraction and screening: **Claude 3 Haiku** (`claude-3-haiku-20240307`), temperature 0.2. Cluster naming, hierarchisation and privacy auditing: **Claude 3.5 Sonnet, June 2024** (`claude-3-5-sonnet-20240620`), temperatures 1, 1.0 and 0.05 respectively. Concern scoring in §4.3: "a model (Claude 3.5 Sonnet from June 2024)". Synthetic-data generation: "a helpful-only version of Claude" (C.2.1, p.27, with a footnote to the Claude 2 model card). Embeddings: `all-mpnet-base-v2` (not a Claude model). Cost table: Claude 3 Haiku for facet extraction, Claude 3.5 Sonnet for labelling and hierarchy. General statement (C.2.2, p.28): "Clio is powered by Claude 3 models". **The whole system as published therefore runs on the Claude 3 family. Every Economic Index release runs a later generation** — Sonnet 3.7 from V2, Sonnet 4 and Sonnet 4.5 later (`wiki/reports/economic-index-2025-03-report.md` Claim 27; `wiki/reports/economic-index-2026-01-report.md` §Classification) — so none of the accuracies in this paper was measured on the model that produced any published Index number. This is the single most important caveat this file exists to record.
- **Validation design, in two independent halves.**
  - **Manual review of each stage in isolation** (Appendix C.1, pp.25–27). n = 200 conversations for the extractor and the concern score (100 random Claude.ai Free/Pro + 100 whose last turn was flagged by production T&S tooling); 5,904 cluster assignments over 183 base clusters (100 random + 83 flagged); 1,094 hierarchical assignments over 183 higher-level clusters (100 random + 84 flagged — the stated total is inconsistent, see Claim 9). Raters are Anthropic staff with authorised access ("A small number of employees can access conversation data for limited business purposes under strict privacy controls", footnote 16, p.26). **The number of raters, the rater instructions beyond one quoted sentence, and any inter-rater agreement statistic are not published**; the human judgement is treated as a single ground truth.
  - **End-to-end synthetic reconstruction** (Appendix C.2, pp.27–30). Two synthetic corpora built top-down: manually specified high-level categories → Claude-generated subcategories → Claude-generated prompts (with length, tone and language randomised) → Claude-generated assistant turns. 19,476 "regular" conversations over 20 top-level categories; 19,488 "concerning" conversations over 18; "evenly distributed across 15 different languages" (per-language n 1,243–1,357, i.e. within ±4.5% of even — the wiki author's arithmetic). Two evaluations: **supervised reconstruction** (Clio clusters freely at base level, then assigns base clusters to the *known* higher-level categories) giving 94% and 84%; and **unsupervised reconstruction**, reported qualitatively only through confusion matrices (Figures 11–14) with no accuracy number. The paper is explicit that the supervised variant is not the full pipeline: "This step is equivalent to the assignment step of our hierarchical clusterer" (C.2.2, p.28). *So the headline 94% measures summarisation plus base clustering plus one assignment step against a ground truth generated by the same model family — **not** Clio's unsupervised discovery of a taxonomy, which is exactly what it does on real traffic.*
  - **Privacy evaluation** (Appendix D, pp.31–32). Auditor applied at three pipeline stages on a Claude.ai sample (5,000 or 25,000; see Claim 14): raw conversations → conversation summaries → cluster summaries. Auditor itself validated on 1,237 hand-built examples with synthetically injected private information.

## Limitations (verbatim)

The paper carries a genuine, itemised limitations section (§5, pp.13–14), split into operational and fundamental, plus ethical risks in §6 (pp.14–16) and a set of bounding statements elsewhere. Quoted in full.

**The framing**

- "While Clio can provide valuable insights into the uses and abuses of AI assistants, it is important to also understand its limitations to prevent overreliance or misuse of the system. These limitations can be broadly categorized into operational limitations and fundamental limitations." (§5, p.13.)
- "Operational limitations arise from imperfections in each stage of the Clio pipeline. These could potentially be mitigated with future advancements in model capabilities, prompt design, and system architecture." (§5.1, p.13.)

**The three operational limitations, verbatim** (§5.1, p.13)

1. "**Extracting facets**: When generating summaries, the model could hallucinate, misinterpret context-dependent phrases or slang, or miss implicit information, such as sarcasm or new news developments."
2. "**Semantic clustering**: The embedding model and k-means algorithm we use can create suboptimal groupings, especially for conversations that don't fit neatly into a single category or for rare, outlier topics."
3. "**Cluster labeling and hierarchization**: Diverse clusters might receive overly broad labels, obscuring important subtopics. Cluster labels may not accurately describe all members of a cluster, or may overemphasize certain topics within a cluster. The hierarchical structure might oversimplify complex relationships between conversation topics, or incorrectly place clusters within the hierarchy."

**The three statements that bound how Clio's outputs may be used** (§5.1, p.13) — *the most important passage in this paper for anyone building on an Index number*

- "While we attempt to quantify many of these sorts of errors in Appendix C, they remain crucial considerations when interpreting Clio's outputs."
- "Given these limitations, we view Clio's outputs as a starting point for generating insights and leads for further investigation. **Its outputs should be considered preliminary and require additional validation before being used as the basis for decision-making.** Taking automated actions based solely on Clio's output would require more rigorous analysis and human oversight to ensure both accuracy and fairness."
- "Furthermore, **Clio cannot conclusively prove the absence of certain patterns or behaviors.** The imperfections in the pipeline or potential adversarial actions could allow harmful behavior to escape undetected by Clio. This underscores the importance of complementing Clio's analysis with other methods."

**The five fundamental limitations, verbatim** (§5.2, pp.13–14)

1. "**Inability to fully capture intent**: While Clio can analyze content and infer topics, it cannot definitively determine user intentions behind a request. Misuses or other harmful behavior might be missed if they are encoded subtly across multiple requests to different models or if the user's true intent differs from how they present it to the model."
2. "**Limited to conversational data**: Clio only analyzes patterns within conversations, not how these conversations translate into real-world actions or impacts. This means we cannot directly observe the full societal effects of AI system use."
3. "**Privacy vs. granularity trade-off**: Our robust privacy measures, while essential, inherently limit the level of detail we can extract from conversations. This may prevent us from identifying some important clusters, including discussions about some public figures or organizations (Appendix D)."
4. "**Our insights are model-specific**: Clio's analysis is based on interactions on Claude.ai. The patterns and insights derived may not generalize to other AI systems, whose underlying capabilities, applications, and user bases may differ considerably."
5. "**Identifying rare behaviors**: Clio will only identify patterns across many different conversations, which means it is not useful for identifying rare (but possibly very consequential) patterns, such as a single example of extreme misuse."
- Closing: "These fundamental limitations underscore the importance of using Clio as part of a broader, multi-faceted approach to understanding the societal impacts of AI systems. While Clio provides valuable insights, it should be complemented by other research methods, **including qualitative studies, user surveys, and real-world impact assessments**." (§5.2, p.14.) *The last clause is the programme the Anthropic Interviewer post and the Economic Index Survey later execute — see `wiki/reports/anthropic-interviewer-2025-12.md` §Definitions, "What the instrument is for, as against Clio".*

Second, we may encounter unforeseen forms of privacy infringement, such as **group privacy violations** [Taylor et al., 2016], where aggregated data could reveal sensitive information about specific communities without revealing information specific to an individual. ## What it did not test

*The wiki author's inference throughout this section, not the paper's own statements.* Each item is something a reader cannot learn from these two documents, or a test the design leaves open. Ordered so that the four items bearing hardest on downstream economic measurement come first.

1. **Classifier drift across model versions is never measured, and every Index number was produced by a model this paper did not validate.** Every accuracy in the paper (Claims 1–10) was measured on the Claude 3 family: Haiku `claude-3-haiku-20240307` for extraction, Sonnet `claude-3-5-sonnet-20240620` for labelling, hierarchisation and auditing. Not one Economic Index release runs that configuration. V2 replaced "all cases where we previously used Claude 3.5 Sonnet" with Sonnet 3.7 (`wiki/reports/economic-index-2025-03-report.md` Claim 27); later waves use Sonnet 4 and Sonnet 4.5 (`wiki/reports/economic-index-2026-01-report.md` §Classification, which concedes that "different models can generate different classification outcomes, though these effects tend to be modest"). **Nowhere — not here, not in any Index report — is the Appendix C validation suite re-run on a later model and the new accuracies published.** So the 96%/97%/94%/98% figures are routinely cited as the validation of measurements they do not describe. Two things follow for our programme. (i) Any post that leans on a published Index accuracy figure must say which model version it was measured on and that the wave in question used a different one. (ii) The one place Anthropic does publish a version-to-version comparison of a headline share — V3's automation share under Sonnet 3.7 against Sonnet 4 — is a single number in an Index report, not a re-validation, and it is the closest thing in the corpus to a drift estimate. *Feasibility question for the steward, not answered here: does any release ship the same window classified under two model versions, at any grain?*
2. **Threshold sensitivity is untestable because the thresholds are not published, and the thresholds are load-bearing.** Layer 2 discards clusters below a minimum on unique accounts *and* conversations; the values are withheld in both documents (and the post states the rule as *or*, not *and* — see Definitions). No run is reported at two threshold settings. No count of discarded clusters, no share of conversations lost to thresholding, and no statement of whether the loss is concentrated in small clusters, particular languages, particular topics or particular account types appears anywhere. Yet the Index's own threshold — "tasks with less than 5 unique accounts or 15 conversations are excluded" — is simultaneously a privacy control and a **denominator rule** ("This also serves to reduce statistical noise", `wiki/reports/economic-index-2025-02-paper.md` p.18), and it defines "task usage" for the depth measure behind the published "~36% of occupations using AI for at least a quarter of their associated tasks". **A share whose denominator is a suppression rule is sensitive to that rule, and no published document reports the sensitivity.** This is a genuinely open empirical question that a post could bound from the public releases without any internal access, by asking how published shares move as the reporting floor is raised — the direction of the bias is knowable even when the original threshold is not.
3. **Multi-turn against single-turn is never separated, and the summary is one construct per conversation regardless of length.** The unit is the conversation; each conversation yields one facet value from a summary capped at "at most two sentences" (G.4, pp.37–38). Turn count is extracted as a facet and used only as an interface overlay and a colour — it is never used as a stratifier in any reported result. The paper's own named failure mode is exactly here: "long, multi-topic conversations where the summary sometimes omitted a subset of the requests from the user in the conversation (in these instances, the model would typically focus on the more harmful requests, if any existed)" (C.1.1, p.26). So summarisation is **biased toward the salient request** in long conversations, with a documented tilt toward harm salience — and no accuracy is reported by turn count, no distribution of turn counts is published for any run, and no result is shown under both sampling strategies, although Strategy 1 is stated to weight longer conversations more (G.1, p.36). For economic measurement this is not a technicality: a multi-turn iterative session and a one-shot delegation are the two ends of the collaboration facet the Index publishes, and the instrument that assigns them compresses both to one two-sentence description. **Whether the automation/augmentation split is confounded with conversation length is not tested here and, as far as this corpus shows, not tested anywhere.**
4. **Language coverage is validated only on synthetic data, and only for reconstruction — never for real non-English traffic, and never for the effect of English-only summarisation.** Table 5's 15 languages are synthetic conversations generated by Claude, summarised in English, embedded with `all-mpnet-base-v2`, and assigned to categories that Claude also generated. Three separate untested links in that chain: (i) **the extractor is instructed to "Output your answer to the question in English"**, so a Japanese conversation becomes an English summary before it is ever embedded — the paper never measures what that translation step loses, and never compares an English-summary pipeline against a native-language one; (ii) `all-mpnet-base-v2` is an English sentence-transformer, and its behaviour on translated-into-English summaries of non-English conversations is not characterised; (iii) the real multilingual result (§3.3, Figure 7) is reported as ratios to base rates with **no accuracy figure for real non-English traffic at all**, and the language facet's own validation is only that Claude's language labels parse as `langcodes` identifiers, which checks the format of the label and not its correctness. The 15 tested languages also exclude, among others, German, Italian, Korean, Indonesian, Vietnamese, Thai, Polish, Dutch, Swedish, Hebrew, Urdu, Bengali and Swahili. **Any Index cut by country inherits all of this**, because usage in a country is usage in its languages; and the Index's own cross-country comparisons never carry a language-coverage caveat.
5. **No re-run, no seed, no stability estimate of any kind.** k is withheld and never varied; the embedding model is never swapped; the summarisation prompt is never varied although the paper states it "influences which conversations get placed close together in the embedding space" (B.2, p.22); temperature 1.0 is used for cluster naming and hierarchisation with no report of how much two runs differ; the hierarchiser's own tolerance band (n*l* ± 1.5n*l*) admits wide variation in the number of clusters per level and no realised value is published. The paper concedes the space is "a continuous manifold… rather than discrete, well-separated clusters" and then reports cluster shares to the nearest percentage point. **There is no published estimate of run-to-run variance for any Clio output, so no published Clio-derived share has a reproducibility interval.**
6. **The 94% headline does not measure what Clio does on real traffic.** It is a *supervised* reconstruction: Clio clusters freely at base level, then the higher level is **fixed to the known ground truth** and Clio only assigns. The paper says so — "This step is equivalent to the assignment step of our hierarchical clusterer" (C.2.2, p.28). On real traffic there is no ground-truth level to be given; Clio must invent the taxonomy, and the unsupervised evaluation of exactly that step (Figures 11–14) is reported **qualitatively, with no accuracy number**. So the most-cited number in the paper describes the easier half of the task.
7. **The ground truth is circular in two places.** The synthetic corpora were generated by Claude from author-specified categories, then reconstructed by Claude: whatever category structure Claude finds natural is present on both sides, and the paper does not estimate how much of the 94% is shared inductive bias rather than accuracy. And in §4.3 Claude's own concern score is "treat[ed] as the ground truth for whether our safety classifiers were classifying correctly" (p.11) on the strength of a ρ = 0.84 rank correlation with human raters on 200 conversations.
8. **Human agreement among the raters is never reported.** Appendix C treats "manual review" as a single ground truth. The number of raters, their instructions beyond one quoted sentence, their training, and any inter-rater agreement statistic are all absent. So the ceiling on every reported accuracy — what two humans would agree on — is unknown, and 96% cannot be placed relative to it.
9. **The unit is the conversation, never the user, and the paper's own account-level check is absent.** Clusters are counted in conversations; the aggregation threshold is the only place accounts appear. There is no reported comparison of conversation-weighted against account-weighted shares in this paper — that check exists, but in the first Index paper ("the patterns of AI usage across occupations remain remarkably stable regardless of which approach we use", `wiki/reports/economic-index-2025-02-paper.md` Claim 38), one release later. For a system that describes itself as analogous to Google Trends, heavy-user weighting is the first thing a reader would want bounded, and this paper does not bound it.
10. **Coverage is never reported: how much traffic never reaches a cluster.** No number is published for conversations dropped by preprocessing, by extractor refusal or failure, by the screener, or by the aggregation thresholds. No run reports "n sampled, n classified, n retained". The paper's own concession that Claude shows "evasiveness" on concerning content (C.2.2, p.28) implies a non-zero refusal rate on real traffic, unmeasured. Any Index denominator is therefore a post-attrition denominator of unknown size, and the "unclassified" residuals that appear in later Index figures (e.g. the 47% + 49% = 96% of `wiki/reports/economic-index-2025-09-blog.md`) have no accounting here.
11. **The four privacy results describe a configuration that safety runs switch off.** §4 (p.9) states plainly that safety-focused runs drop the aggregation thresholds and the cluster auditing, and can be relinked to individual accounts. Two of the four privacy layers are therefore absent from a use of the system the paper describes at length, and **no privacy evaluation of the safety configuration is published**. Nothing here is a criticism of the design — the purpose requires it — but it means "Clio is privacy-preserving" is a claim about one configuration, and readers of the Index (which uses the research configuration) and readers of the enforcement case studies (which do not) are being told about different systems.
12. **Privacy is tested against a rubric, not against re-identification.** No linkage attack, no membership-inference test, no adversarial attempt by a party outside the authoring team, no external audit. Level 3 — "narrow identification to several thousand people" — is scored as acceptable. Group privacy is raised in §6.2 as a risk and is not evaluated at all, and the stated worry about **correlated failures across stages** is exactly what a stage-by-stage audit cannot detect, since all four stages are prompted Claude models sharing a training lineage.
13. **The auditor's negatives are synthetic, so its 98% is not a field error rate.** The 630 "not privacy preserving" examples were made by injecting fictional private information into real privacy-preserving clusters (D.1, p.32). That set is, by construction, drawn from the failure modes the authors thought of. The auditor's accuracy against privacy failures *nobody anticipated* — the case §6.2 names as the residual risk — is untested by design.
14. **The cost claim excludes almost everything and is internally inconsistent with the paper's own procedure.** $48.81 per 100,000 conversations covers three inference steps, priced at list, under assumptions (see Claim 16) whose cluster-labelling token count is roughly an order of magnitude below what G.5's stated 50-plus-50-summary sampling implies. It excludes embedding, k-means, UMAP, the secure environment, storage, the interface, engineering and — most importantly — the human validation that the paper itself says Clio's outputs "require" before use. And it is never compared to the cost of the human review it replaces, so "relative affordability" has no denominator.
15. **No human-analyst baseline, for accuracy or for discovery.** Nobody ran a team of analysts over the same 1M conversations to ask what they would have found. The paper's central pitch — bottom-up discovery of unknown unknowns at a scale humans cannot reach — is demonstrated by existence proof (three enforcement cases, two monitoring episodes) and never measured: no recall against a known set of planted patterns, no comparison against string matching or against the production classifiers on discovery (only on agreement), and no false-discovery rate for clusters flagged and then cleared.
16. **Conversations are not linked to anything outside the conversation.** §5.2 item 2 says it: "Clio only analyzes patterns within conversations, not how these conversations translate into real-world actions or impacts." So no outcome, no firm, no wage, no employment, no productivity, no demographic and no account attribute is joined to any cluster in this paper. Combined with the extractor's "do not include any proper nouns" instruction, this means **firm-level and institution-level economic measurement is foreclosed at the summarisation step**, not merely unattempted: the employer, the product, the university and the place are stripped before anything is clustered. Any brief proposing to identify firms, sectors-by-employer or institutions from Clio-derived Index data should treat that as a hard constraint and say so.
17. **Geography is stated not to be supported, and the Index publishes geography.** "Clio does not support analysis based on geography" (§6.4, p.15). Every Index release from March 2025 on publishes country and US-state cuts and an AI Usage Index. **This file cannot reconcile the two**, and no post should assume the Index's geography comes from the pipeline described here. The candidate reconciliations — a later capability, a join performed outside Clio on account metadata, or a different privacy regime for geographic aggregates — are all conjecture from this document. *Room note to the steward and a re-read of the Index appendices are the right next steps; this is flagged in the accompanying note.*
18. **Whether the *set* of facets biases what can be found is not examined.** Four facets were used: Request, Language, Task, Concerning. The paper states that the summarisation prompt determines the embedding geometry and therefore the clusters. It does not report the same corpus clustered under two different facets to show how much the discovered structure depends on the question asked. **Everything the Economic Index measures is a facet choice**, and this paper — the one place the facet mechanism is documented — never demonstrates facet sensitivity.
19. **The false-positive and false-negative analysis has no rates.** Three named false-positive clusters, two false-negative flag rates (60%, 31%), no denominators, no cluster sizes, no overall false-positive or false-negative rate for either system, and no follow-up measuring whether the classifiers improved after the findings were acted on. The figure that carries the comparison drops all clusters below 1.75 on the concern axis, and the correlation is not reported separately for truncated and untruncated sets.
20. **Nothing is checked over time.** All four runs fall in a five-week window, 17 October to 14 November 2024, and none of them overlaps another completely. There is no test of whether the same pipeline applied to two periods yields comparable clusters — the elementary precondition for the Economic Index's entire enterprise, which is comparison across waves. The interface offers temporal breakdowns (B.4, p.23) and no temporal result is reported. **The paper that licenses every Index time series contains no time series and no stability-over-time check.**
21. **"Analogous to Google Trends" is offered as a framing and never examined as a claim.** Google Trends publishes a normalised, documented index with known suppression rules and a public API. Clio publishes neither its k, nor its thresholds, nor its intermediate objects, and its cluster boundaries move with the prompt. The analogy is rhetorically load-bearing — it is how the post introduces the system — and no property of Google Trends is actually shown to hold of Clio.
22. **Cross-system generalisation is asserted as a limitation and partly contradicted by the paper's own evidence.** §5.2 item 4 says insights "may not generalize to other AI systems". Appendix E then shows they demonstrably do not: WildChat and LMSYS have visibly different top-level distributions. But the paper reports that contrast only qualitatively, with a shared 15–25% coding band and the word "significantly", and never reports the Claude.ai coding share on the same basis — so the size of the difference between Claude.ai and public corpora, the one quantity that would calibrate how far any Claude finding travels, is not published. **This is a live and tractable question:** WildChat and LMSYS-Chat-1M are public, so the comparison the paper declined to quantify is the rare Clio question an outside team can actually pursue — though without Clio itself, only with a reimplementation, which is a different instrument.
23. **The relationship between this system and the Index's own constructs is not documented anywhere in this paper, and needs to be, because the constructs are not interchangeable.** A Clio cluster is a k-means neighbourhood in summary-embedding space with a Claude-written imperative name, not guaranteed unique (footnote 4), ~3% contaminated on average (Claim 8), of withheld granularity. An O\*NET task group is an external, fixed, human-curated taxonomy. The Index maps the first onto the second and publishes shares over the result. **Neither this paper nor any Index report in this corpus publishes an accuracy figure for that mapping step measured against human judgement** — the first Index report says only "it is possible that Clio classified some conversations incorrectly (please see the full paper, in particular Appendix B, for details on how we validated the analysis)" and points back to this paper, whose Appendix C validates cluster titling and hierarchy assignment on Clio's *own* taxonomy, not on O\*NET.
